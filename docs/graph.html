Graph engineering · project Tars

Tars build — the run graph

Five chained workflows with the main session (me + you) as the decision point between them. Two constraints shape everything: auth needs your logged-in browser, which only the main session may drive — and the Slack-app cutover is destructive, so it is a gate, never an unattended node.

Why this shape

  • Auth is a lane, not a node. Every credential needs your logged-in browser, and the browser is main-session-only (subagent typing lands in your active tab). So acquisition is serial human work — but each acquired credential immediately fans out an async probe agent, so testing never blocks acquiring the next one.
  • Your hint, applied: WF2 (VM provisioning) needs zero credentials from lane A — Proxmox and tailscale access already exist on cooper. It runs fully unattended in parallel. Only the join (wiring creds into Hermes on the VM) needs both.
  • The cutover is a gate, not a graph node. Deleting the old Tars profile on your personal Hermes is destructive and the Slack app can only live in one place. Sequenced so nothing is deleted until the new side is provisioned, wired, and smoke-tested — with before-evidence captured first.
  • WF4 exists because of the silent-green rule. A wired integration that never fired counts as not done. Fourteen probes, each returning a schema verdict with evidence — including the negative test: a message from someone who isn't you must be ignored. A completeness critic asks what's untested; gaps loop back.

Critical path

WF1 → max(lane A, lane B) → WF3 → cutover → WF4. Lane A is the long pole — it's the only part that needs you. Everything else is machine time, and I stay the orchestrator between workflows: read each phase's results, decide, launch the next.
